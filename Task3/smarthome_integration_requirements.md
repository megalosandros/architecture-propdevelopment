# Требования к интеграции сервисов "Умный дом"

## 1. Требования к безопасности

### 1.1. Защита персональных данных
 - Все биометрические данные (изображения лиц, шаблоны распознавания) не передаются на сторону партнёра.
   - Обработка должна происходить локально (на устройстве или на приватном edge-оборудовании в ЖК).
 - Номера транспортных средств (ГРЗ) классифицируются как конфиденциальные данные и передаются только при наличии согласия собственника.
 - Партнёр не имеет права хранить, копировать, анализировать или использовать данные в целях, не связанных напрямую с функцией сервиса.

### 1.2. Минимизация данных (Data Minimization)
 - API должен возвращать только статус операции (allowed/denied) и минимальный технический контекст (например, timestamp, camera_id).
 - Запрещено передавать:
   - ФИО собственника,
   - список всех жильцов,
   - данные о других автомобилях или лицах.

### 1.3. Шифрование
 - Все данные при передаче — обязательно по TLS 1.2+.
 - Если данные всё же хранятся у партнёра (например, хэши ГРЗ), они должны быть зашифрованы at rest (AES-256 или аналог).
 - Ключи шифрования не передаются партнёру — хранятся в Vault PropDevelopment.

### 1.4. Соответствие законодательству
 - Партнёр обязан подписать договор о передаче персональных данных с указанием роли «оператора по поручению оператора» (ст. 6 ФЗ-152).
 - Обработка биометрических данных возможна только с письменного согласия собственника.
 - PropDevelopment сохраняет полную ответственность за обработку ПДн.

## 2. Протоколы аутентификации и авторизации

### 2.1. Аутентификация партнёра
 - Партнёрская платформа аутентифицируется с использованием mTLS (mutual TLS) или OAuth 2.0 Client Credentials с выданным client_id/client_secret.
 - Секреты хранятся в HashiCorp Vault (или аналоге), не в коде и не в конфигах.

### 2.2. Авторизация вызовов
 - Все запросы от PropDevelopment к партнёрскому API должны содержать access token с ограниченными scope:
   - domophone:open — только открытие двери,
   - barrier:open — только открытие шлагбаума.
 - Сервер партнёра проверяет scope и не выполняет действия вне него.

### 2.3. Контекст пользователя
 - При вызове API из мобильного приложения PropDevelopment передаёт:
   - user_id (внутренний идентификатор собственника),
   - device_id,
   - timestamp,
   - geolocation (опционально, для проверки проксимальности).
 - Никакие ПДн (ФИО, номер телефона и т.п.) не передаются.

## 3. Организация взаимодействия между системами

### 3.1. Архитектурный паттерн
 - Используется паттерн «API Gateway + Adapter»:
 - Мобильное приложение → tenant-core-app (PropDevelopment) → PropDevelopment Integration Gateway → Партнёрский API.
 - Все вызовы проходят через внутренний прокси, который:
   - логирует запросы,
   - проверяет rate-limit,
   - маскирует внутренние идентификаторы,
   - блокирует подозрительные паттерны.

### 3.2. Технологический стек
 - Протокол: HTTPS/REST (или gRPC при высокой нагрузке).
 - Формат: JSON, с чёткой схемой (OpenAPI 3.0).
 - Идемпотентность: все операции POST /open должны быть идемпотентными (защита от повторных вызовов).

### 3.3. Логирование и аудит
 - Все вызовы логируются в централизованную систему (SIEM) с полями:
   - timestamp,
   - user_id,
   - action,
   - result,
   - partner_request_id.
 - Логи хранятся не менее 6 месяцев (требование ФЗ-152).
 - Доступ к логам — только для ИБ-команды и аудиторов.

### 3.4. Отказоустойчивость
 - Партнёр обязан обеспечить SLA ≥ 99.5%.
 - При недоступности партнёра:
   - tenant-core-app переходит в режим «классический домофон/шлагбаум» (по коду или RFID),
   - пользователю отображается уведомление: «Биометрия временно недоступна».

### 3.5. Тестирование и мониторинг
 - Перед запуском — пентест API партнёра.
 - В продакшене — ежедневный health-check и мониторинг latency/error rate.
 - Любое отклонение от SLA триггерит оповещение в DevOps и ИБ.

## 1. Требования к безопасности

### 1.1 Аутентификация и авторизация

#### 1.1.1 Протоколы аутентификации
- **OAuth 2.0 с PKCE** - основной протокол для аутентификации между системами
- **JWT (JSON Web Token)** - для передачи токенов доступа
- **mTLS (Mutual TLS)** - для взаимной аутентификации на транспортном уровне
- **API Key** - для сервис-сервис взаимодействия (в качестве дополнительного уровня)

#### 1.1.2 Протоколы авторизации
- **RBAC (Role-Based Access Control)** - управление доступом на основе ролей
- **ABAC (Attribute-Based Access Control)** - для сложных политик доступа
- **Scope-based authorization** - ограничение доступа к конкретным ресурсам
- **JWT Claims** - для передачи информации о правах доступа

### 1.2 Шифрование данных

#### 1.2.1 Шифрование в покое
- **AES-256** - для шифрования данных в базах данных
- **TDE (Transparent Data Encryption)** - для PostgreSQL
- **Encryption at rest** - для всех хранимых данных

#### 1.2.2 Шифрование в передаче
- **TLS 1.3** - для всех HTTP/HTTPS соединений
- **End-to-end encryption** - для критически важных данных
- **Certificate pinning** - для мобильных приложений

### 1.3 Защита персональных данных

#### 1.3.1 Биометрические данные
- **Локальное хранение** - биометрические шаблоны хранятся только на устройствах
- **Хеширование** - невозможность восстановления исходных биометрических данных
- **GDPR compliance** - соответствие требованиям защиты персональных данных
- **Согласие пользователя** - явное согласие на обработку биометрических данных

#### 1.3.2 Логи доступа
- **Анонимизация** - удаление персональных данных из логов
- **Retention policy** - политика хранения логов (максимум 1 год)
- **Audit trail** - полная трассировка всех операций доступа

### 1.4 Сетевая безопасность

#### 1.4.1 Firewall и сегментация
- **Network segmentation** - изоляция IoT устройств в отдельной сети
- **VPN туннели** - для связи с внешними системами
- **Intrusion Detection System (IDS)** - мониторинг сетевого трафика
- **DDoS protection** - защита от атак типа "отказ в обслуживании"

#### 1.4.2 IoT безопасность
- **Device certificates** - сертификаты для всех IoT устройств
- **Secure boot** - защищенная загрузка устройств
- **Firmware updates** - безопасное обновление прошивки
- **Device authentication** - аутентификация устройств перед доступом к сети

## 2. Протоколы взаимодействия между системами

### 2.1 Взаимодействие PropDevelopment ↔ Платформа умного дома

#### 2.1.1 Основной протокол
- **HTTPS/REST API** - основной протокол взаимодействия
- **JSON** - формат обмена данными
- **HTTP/2** - для улучшения производительности

#### 2.1.2 Аутентификация
```
POST /oauth/token
{
  "grant_type": "client_credentials",
  "client_id": "propdev_client",
  "client_secret": "***",
  "scope": "smart_home:manage"
}
```

#### 2.1.3 Авторизация
- **Bearer Token** в заголовке Authorization
- **Scope-based permissions**: 
  - `smart_home:read` - чтение данных устройств
  - `smart_home:manage` - управление устройствами
  - `smart_home:events` - получение событий

### 2.2 Взаимодействие с IoT устройствами

#### 2.2.1 Протоколы IoT
- **MQTT over TLS** - для обмена сообщениями с устройствами
- **CoAP over DTLS** - для ресурсоограниченных устройств
- **HTTP/HTTPS** - для управления устройствами

#### 2.2.2 Структура сообщений
```json
{
  "device_id": "doorbell_001",
  "timestamp": "2024-01-15T10:30:00Z",
  "event_type": "access_granted",
  "user_id": "user_123",
  "biometric_match": true,
  "confidence": 0.95
}
```

## 3. Архитектура интеграции

### 3.1 Компоненты системы

#### 3.1.1 Smart Home Integration Service
- **Назначение**: Центральный сервис интеграции с платформой умного дома
- **Технологии**: Kotlin, Spring Boot, PostgreSQL
- **Функции**:
  - Аутентификация с внешней платформой
  - Синхронизация данных пользователей
  - Управление устройствами
  - Обработка событий

#### 3.1.2 Notification Service
- **Назначение**: Отправка уведомлений о событиях умного дома
- **Технологии**: Kotlin, Spring Boot, Redis
- **Функции**:
  - Push уведомления в мобильное приложение
  - Email уведомления
  - SMS уведомления (для критических событий)

#### 3.1.3 Smart Home Database
- **Назначение**: Хранение настроек и логов умного дома
- **Технологии**: PostgreSQL 14+
- **Структура**:
  - Пользователи и их устройства
  - Настройки доступа
  - Логи событий
  - Статистика использования

### 3.2 Потоки данных

#### 3.2.1 Поток управления устройством
```
Мобильное приложение → Tenant Core → Smart Home Service → Внешняя платформа → IoT устройство
```

#### 3.2.2 Поток событий
```
IoT устройство → Внешняя платформа → Smart Home Service → Notification Service → Мобильное приложение
```

#### 3.2.3 Поток синхронизации пользователей
```
CRM → Tenant Core → Smart Home Service → Внешняя платформа → IoT устройства
```

## 4. Требования к производительности и надежности

### 4.1 Производительность
- **Response time**: < 2 секунд для операций управления
- **Throughput**: поддержка 1000+ одновременных пользователей
- **Availability**: 99.9% времени доступности

### 4.2 Надежность
- **Circuit breaker** - защита от каскадных отказов
- **Retry mechanism** - повторные попытки при сбоях
- **Graceful degradation** - деградация функциональности при сбоях
- **Health checks** - мониторинг состояния сервисов

### 4.3 Мониторинг и логирование
- **Distributed tracing** - трассировка запросов между сервисами
- **Metrics collection** - сбор метрик производительности
- **Centralized logging** - централизованное логирование
- **Alerting** - уведомления о критических событиях

## 5. Требования к соответствию стандартам

### 5.1 Соответствие регулятивным требованиям
- **GDPR** - защита персональных данных в ЕС
- **152-ФЗ** - защита персональных данных в РФ
- **ISO 27001** - управление информационной безопасностью

### 5.2 Технические стандарты
- **RFC 6749** - OAuth 2.0 Authorization Framework
- **RFC 7519** - JSON Web Token (JWT)
- **RFC 8446** - TLS 1.3
- **ISO/IEC 27040** - хранение данных

## 7. Риски и митигация

### 7.1 Технические риски
- **Сбой внешней платформы**: резервные каналы связи
- **Проблемы с производительностью**: горизонтальное масштабирование
- **Уязвимости безопасности**: регулярные аудиты безопасности

### 7.2 Операционные риски
- **Недоступность сервиса**: мониторинг 24/7
- **Потеря данных**: резервное копирование
- **Неправильная конфигурация**: автоматизация развертывания
